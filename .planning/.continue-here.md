## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Silent-noop on pattern-match fail | Adapter helpers that do `if (!match) return content` silently drop writes when hardcoded heading regexes don't match real-world STATE.md variants. Handler falsely reports success. | blocking | Adapter helpers in `adapters/markdown/index.ts` now use `appendToOrCreateSection` (create-if-missing) for additive events. The StateWriteOutcome contract (designed, not yet implemented) would close the gap by returning `{applied: false, reason}` so callers know. NEVER reintroduce `appendToSection` — it was deleted from the codebase for exactly this reason. |
| Bundled executor commit with file corruption | An executor agent produced a commit (88d43deb) that bundled a legitimate refactor with file-corrupting edits (missing closing braces, dangling JSDoc). One build step would have caught it; one test run would have caught it. The commit landed anyway via a worktree auto-merge. | blocking | Execute plans as atomic per-file commits with a build + test gate after each file. `/gsd-execute-phase` worktree agents should NOT bundle multi-file refactors into one commit — split by file or by logical unit. See commit trail 49a5f6cb, 11dc85a3, 6070d319, b22606a9 for the atomic-re-do pattern. |
| Competing derived-field writers | Two code paths wrote `progress.completed_phases` / `progress.percent` with different formulas (phase-weighted vs plan-weighted). Consecutive adapter writes produced different values; nothing was a stable source of truth. | advisory | Derived frontmatter fields (progress.*, last_updated, status normalization) must have exactly one writer. `syncStateFrontmatter` in sdk/src/query/state.ts is now the sole writer of all 5 progress fields. Any future code that needs to update progress should write SUMMARY.md files and let the sync derive the counters. |

## Pre-Execution Critique Required

If resuming into the StateWriteOutcome contract refactor, the following questions should be answered before writing code:

- Should `recordStateSignal` also return `StateWriteOutcome`? It's `resume`/`waiting` semantics — the `nothing_to_remove` case is legitimate (signal-resume when no WAITING.json existed). Currently returns `void`.
- Should `workstream` be a first-class field on the outcome? Some callers need to know which workstream's STATE.md was written to (multi-workstream repos).
- How should `stateAddRoadmapEvolution`'s current double-dedupe (handler-side pre-check + adapter-side dedupe) be resolved? Simplest: remove the handler-side check and trust the adapter's outcome.
- Regression test coverage: should be minimum one test per (event type × outcome value). 5 event types × 3 outcome values = up to 15 tests; some are vacuous (quick_task never produces `nothing_to_remove`).
